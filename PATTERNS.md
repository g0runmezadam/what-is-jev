# Recurring patterns

Last reviewed: 2026-09-20 · Every pattern here appears in at least two of the 785 scored repositories, each read at README depth (not the code) against the rubric in [`data/rubric.md`](data/rubric.md). Scores are an LLM's judgment, not a benchmark of the projects themselves — method and limits in [`METHODOLOGY.md`](METHODOLOGY.md). A single-repo idea is not a pattern; those are collected at the end instead. Where a repo says it measured something, that means **the repo's own authors measured it on their own data**, not an independent check — treat it the same way [`FINDINGS.md`](FINDINGS.md) treats vendor claims.

## 1. The baseline decision machine

Batch several typed questions over one state, apply a threshold, keep an "uncertain" band for values near it, fall back to a rule or a bigger model, and log the decision. This is close to universal: nearly every serious Jev project in this map does some version of it, and the [rubric](data/rubric.md) treats it as the zero point that novelty is scored against. It works because it turns one noisy probability into a decision with a known escape hatch. It fails when the threshold and band are picked once and never checked against real outcomes — several repos below exist specifically to fix that.

Evidence: [DevMortimer/pi-warden](https://github.com/DevMortimer/pi-warden), [coldteadotai/abide](https://github.com/coldteadotai/abide), [thevibeworks/jevgate](https://github.com/thevibeworks/jevgate), [ddfeyes/jev-mode](https://github.com/ddfeyes/jev-mode), [de-niji/jev-hermes](https://github.com/de-niji/jev-hermes).

## 2. Code decides facts, the model judges only the grey zone

Deterministic rules run first and settle everything they can; Jev is asked only about the part that needs judgment, and its answer can narrow permission but never widen it past what the rules allow. `thevibeworks/jevgate` reports that in real traffic 26% of decisions are settled by code and 16% by the model — the rest is proven or refused without a call. `godspede/construct-auto-classifier` runs fast rules, script provenance and a retry counter before any model call, and only Jev among ten certified models reached zero dangerous commands allowed across 975 decisions (two frozen test sets, five passes each). This fails when the "grey zone" quietly grows to include cases the deterministic layer could have handled, which raises cost without raising safety.

Evidence: [thevibeworks/jevgate](https://github.com/thevibeworks/jevgate), [godspede/construct-auto-classifier](https://github.com/godspede/construct-auto-classifier), [qkal/Canny](https://github.com/qkal/Canny), [buberlo/dsh-jev](https://github.com/buberlo/dsh-jev), [zyphr-labs/turnstile](https://github.com/zyphr-labs/turnstile).

## 3. Tool-call gates and permission firewalls for coding agents

A hook fires before a tool call (PreToolUse or equivalent), asks Jev a small set of typed risk questions about the command or diff, and returns deny/ask/allow. `leepokai/jev-guard` runs this across eight different coding agents with four question types, where one signal — content that looks like it is following an instruction planted in something the agent read — is a deny on its own regardless of computed risk. `RiskAverseTech/toolgate` documents both directions of the fail-safe choice explicitly: in unattended permission modes a would-be "ask" becomes a deny by default, and if the model itself is unreachable the gate's own internal errors always resolve to "ask", never a silent allow. `agent-chaperone` scans tool results the agent has not yet read, reporting AUC 0.976 on InjecAgent and 1.000 on BIPIA email test sets (authors' own measurement). The failure mode across this family is scope creep: a gate tuned on synthetic or hand-written commands does not automatically hold on real traffic (measured by the authors, not independently verified).

Evidence: [leepokai/jev-guard](https://github.com/leepokai/jev-guard), [RiskAverseTech/toolgate](https://github.com/RiskAverseTech/toolgate), [agent-chaperone/agent-chaperone](https://github.com/agent-chaperone/agent-chaperone), [RahulBalakavi/claude-code-jev](https://github.com/RahulBalakavi/claude-code-jev).

## 4. Steer, don't block

Instead of stopping the agent when it violates a constraint, feed the violation back into its own context so it corrects course on the next step. `DevMortimer/pi-warden` measured this directly against a hard-block control: in 150 paired agent runs, the control setup violated the tested rule 6 times; the steering setup, 0 (authors' own paired A/B, not independently reproduced). `Nyarlathoteppppp/pi-heed` turns a user-stated constraint into a standing policy that survives compaction and gets replayed back to the agent rather than enforced by a hard stop. This works when the model can act on feedback in-context; it fails for actions that are irreversible the moment they run, where a hard block is the only honest option (see pattern 12).

Evidence: [DevMortimer/pi-warden](https://github.com/DevMortimer/pi-warden), [Nyarlathoteppppp/pi-heed](https://github.com/Nyarlathoteppppp/pi-heed).

## 5. Rule-compliance checks against AGENTS.md / CLAUDE.md

Turn the prose rules in a project's agent-instruction file into typed Jev questions, and check every edit or every commit against them instead of relying on a human reviewer to remember all of them. `coldteadotai/abide` replayed 93 real Claude Code sessions (1,256 edits, 147 turns) against their own project's AGENTS.md and found a rule broken on roughly one turn in 13, with an independent human reviewer confirming most of the flagged edits; it also auto-disables rules that never fire, so the check set does not silently grow stale. `zoidsh/tenet` splits AGENTS.md/CLAUDE.md into individual sentences, asks Jev whether each is checkable, and reports its own comparison against calling a chat model for the same job (faster and cheaper by the authors' measurement) — the duplicate registration `zoidsh/tenetlint` shares the identical README and is not counted separately. `rashedInt32/jev-gates` is deliberately asymmetric: six gates over rule/scope/intent/completion/claims/commit, and none of the six is allowed to approve — only escalate.

Evidence: [coldteadotai/abide](https://github.com/coldteadotai/abide), [zoidsh/tenet](https://github.com/zoidsh/tenet), [rashedInt32/jev-gates](https://github.com/rashedInt32/jev-gates).

## 6. Context reduction: compaction and tool-output sieves

Cut a large tool result or growing context into blocks, ask Jev per block whether the current task still needs it, and hide only what is confidently useless — never summarize the parts that are kept, so nothing is silently rewritten. `dizk/jev-lens` measured this on 500 real agent trajectories (11.6 million tokens) and reports 79% fewer tokens sent for large tool results, with a harm rate of roughly 2% (missed edits or dropped identifiers); it also found that pruning after the first send breaks the prompt cache and cost 17% more in their own runs, so the design compresses before the first send instead. `GhalebDweikat/winnow` sets its drop threshold from hand-labeled replay rather than a guess, and keeps anything merely uncertain rather than anything merely unselected. `Nyarlathoteppppp/pi-jev-context` is the sharpest caveat in this group: a synthetic benchmark showed 11–12.5% of dropped context was later needed, but on real sessions the same measurement rose to 73% — which is why that project logs what it would prune instead of actually deleting it. Independently, a benchmark outside this repository's corpus found the opposite result for a different task shape: scoring browser-agent context with Jev cut task time but raised total cost 38–51% because the scoring calls themselves dominated spend — see [`FINDINGS.md`](FINDINGS.md#3-speed-cost-and-accuracy-claims). Compaction is not automatically a saving; measure the scoring cost, not just the token cut.

Evidence: [dizk/jev-lens](https://github.com/dizk/jev-lens), [GhalebDweikat/winnow](https://github.com/GhalebDweikat/winnow), [Nyarlathoteppppp/pi-jev-context](https://github.com/Nyarlathoteppppp/pi-jev-context), [QuentinDanblon/pi-fast-jev-compaction](https://github.com/QuentinDanblon/pi-fast-jev-compaction).

## 7. Routing: model and skill routers

Two-stage routing — a cheap wide pass narrows a large catalog, then a second pass picks among the survivors — plus an explicit "none of these" option so the router can decline rather than force a bad match. `GodsBoy/jev-agent-skill-router` narrows a catalog of 443+ skills through parallel Jev batches and reports 68 of 72 exact routing outcomes correct (94.4%) against 51 of 72 (70.8%) for a lexical baseline, on the authors' own exploratory test set — the same README calls this "exploratory, reused-data" and notes an earlier run scored lower before the questions were revised, so read it as a promising in-house number, not an independent benchmark. `FirasSX914/Janus` measures its routing threshold per task rather than assuming one holds everywhere, and is willing to answer "do not route" when no confident option exists. `0xNatoshi/jev-codex-router` adds a rule-based middle tier for low-confidence cases instead of forcing a routing decision at low confidence.

Evidence: [GodsBoy/jev-agent-skill-router](https://github.com/GodsBoy/jev-agent-skill-router), [DECRUX9812/typesafe-skill-router](https://github.com/DECRUX9812/typesafe-skill-router), [0xNatoshi/jev-codex-router](https://github.com/0xNatoshi/jev-codex-router), [FirasSX914/Janus](https://github.com/FirasSX914/Janus).

## 8. Voting, non-determinism, and splitting compound questions

Three related findings recur. First, voting or averaging near a decision boundary reduces the effect of run-to-run noise: `copyleftdev/jev-labs` model-checked a consensus protocol in TLA+ and ran it 1,680 times against the live API under seeded chaos, reporting zero wrong verdicts across 1,080 "golden" rounds. Second, Jev is not deterministic call to call: `yodablocks/commitjev` measured a 0.01–0.06 spread per rule across four runs of the same thirteen calibration cases. Third, and most concretely, a compound question reads worse than the same question split in two: `commitjev` asked "removed, and unexplained" as one question and Jev answered by reading only the first half, scoring the wrong commit higher than the right one (0.81 vs 0.75); split into two separate questions the scores moved to 0.99 vs 0.04. A fourth, related effect — answer order changing the result — is measured, not assumed, in one source: `RINNECODER/jev-behavior-study` ran 11,621 requests and found 95/108 correct when the right answer was listed first versus 62/108 when it was listed last, and separately found that facts placed in the middle of a long context were missed more often than facts at the edges (both the authors' own measurement, a single study).

Evidence: [copyleftdev/jev-labs](https://github.com/copyleftdev/jev-labs), [yodablocks/commitjev](https://github.com/yodablocks/commitjev), [RINNECODER/jev-behavior-study](https://github.com/RINNECODER/jev-behavior-study), [totally-tim/jev-gate](https://github.com/totally-tim/jev-gate).

## 9. Calibration and evaluation discipline

The most useful projects in this map are the ones that refuse to trust "the test suite passed" as evidence. `JYeswak/jev_playground` ran 22 launch-week Jev repositories and found that substituting a well-formed random judge for Jev still left 254 of 305 tests green (83%) — a suite that passes a coin flip is plumbing, not validation. `collapseindex/dinostomp` tests each Jev question the way you would test a unit of code: accuracy, calibration, the best cut point, and a bias baseline, logging 191 findings. `Adilmp/does-jev-confidence-mean-anything` ran 8,000 judgments against human labels and is one of the sources behind the calibration finding in [`FINDINGS.md`](FINDINGS.md#4-calibration--does-09-mean-90) — probabilities were shifted toward "yes," while ranking quality (AUC) stayed good, meaning the ordering was right and the units were wrong. The recurring lesson across this group, stated independently by more than one project, is that a labelled set built from real sessions catches failures a synthetic or self-authored test set does not (see pattern 6's `pi-jev-context` numbers for the same effect measured a different way).

Evidence: [JYeswak/jev_playground](https://github.com/JYeswak/jev_playground), [collapseindex/dinostomp](https://github.com/collapseindex/dinostomp), [Adilmp/does-jev-confidence-mean-anything](https://github.com/Adilmp/does-jev-confidence-mean-anything), [meetr1912/jev-arena](https://github.com/meetr1912/jev-arena).

## 10. Hooks are needed — availability is not enough

An MCP tool that an agent could call is not the same as a tool the agent will call. `Dharundp6/jev-carryforward`'s own plugin evaluation found that with the recall tool installed and available, the agent called it zero times out of four runs on a task specifically designed to require it — it answered from what it believed it already knew and proposed the wrong git command. The project's conclusion, stated in its own README, is why the tool now also runs from a `SessionStart` hook that injects the recalled facts unconditionally rather than depending on the model choosing to look. The same caution appears in the report notes for `ddfeyes/jev-mode`, which found that a sub-agent spawned mid-session does not automatically inherit the parent's hooks — a gap that has to be closed explicitly, not assumed away.

Evidence: [Dharundp6/jev-carryforward](https://github.com/Dharundp6/jev-carryforward), [ddfeyes/jev-mode](https://github.com/ddfeyes/jev-mode).

## 11. Local reproductions of Jev from open models

Several groups rebuild a Jev-shaped interface — typed questions in, a probability out, no free text — on top of an open model, usually by reading option-token logits directly instead of decoding text. These are reproductions, not integrations: this repository's data marks `TheoLeeCJ/openjev` and `yohanargentina-oss/Foq` as `calls_jev: no`, which is expected here — the whole point of a local reproduction is to run without calling the real API, and any comparison numbers below come from the authors testing their own build against Jev's published outputs, not from a live call inside the project. `TheoLeeCJ/openjev` (registered a second time under the renamed `TheoLeeCJ/Semif`) reports 0.845 modal agreement with the published Jev model on a TypeSafe-selected comparison subset — an agreement measurement against the real vendor model, not just the authors' own labels. `DECRUX9812/openjev-lm` distills toward Jev's outputs and reports 92.9% accuracy for a CPU-only model at effectively zero marginal cost per call — measured against the authors' own distillation target. `Heman10x-NGU/openJev-verdict-2.0` reports 77.1% top-1 accuracy for its 150M-parameter model against 72.7% it measured for TypeSafe Jev 1.13.0 on the same cases — this comparison runs entirely on the authors' own constructed test set with their own labels, not an independently held-out benchmark, so read the "beats Jev" framing with that caveat; the same caveat applies to `yohanargentina-oss/Foq` and `wfzyx/von`, which report similar own-test-set comparisons.

Evidence: [TheoLeeCJ/openjev](https://github.com/TheoLeeCJ/openjev), [DECRUX9812/openjev-lm](https://github.com/DECRUX9812/openjev-lm), [Heman10x-NGU/openJev-verdict-2.0](https://github.com/Heman10x-NGU/openJev-verdict-2.0), [yohanargentina-oss/Foq](https://github.com/yohanargentina-oss/Foq).

## 12. Where Jev should not drive

The vendor's own weakness list — literal reading, math, dates, generation, adversarial content (see [`FINDINGS.md`](FINDINGS.md#2-what-cannot-hallucinate-actually-means)) — shows up as lived experience in this corpus, and the honest negative results are some of the most useful entries in the whole map. `pcarrier/skibidu` tried to have Jev construct an entire program's abstract syntax tree node by node with no free-text generation at all, and its own README calls the result impractical: a small arithmetic interpreter alone needs hundreds of construction calls, and success on that fixture is explicitly not evidence the approach converges on anything larger. `wei-b0/gram-render` states the pattern as a rule rather than a lesson learned the hard way: the generation layer never writes prose, it only ever selects among candidates that something else proposed. `rhighs/jev-code` names the resulting division of labor directly — the language model proposes, Jev approves or picks — as the design that avoids `skibidu`'s failure mode.

Evidence: [pcarrier/skibidu](https://github.com/pcarrier/skibidu), [wei-b0/gram-render](https://github.com/wei-b0/gram-render), [rhighs/jev-code](https://github.com/rhighs/jev-code).

## Single-repo ideas worth watching

Each of these appears once in the corpus, so it is an idea, not a pattern yet.

- [meetr1912/jev-vickrey](https://github.com/meetr1912/jev-vickrey) — build a value's survival curve from a series of threshold questions ("is it above X?") instead of trusting one raw probability.
- [voidning/jev-combinators](https://github.com/voidning/jev-combinators) — Cascade/Gate/Vote as composable building blocks instead of one bespoke decision function per project.
- [CaseReed/latch](https://github.com/CaseReed/latch) — cluster CI failures by signature and stop re-asking Jev the same "is this environment noise?" question once it has answered.
- [adarc8/how-sure-is-jev](https://github.com/adarc8/how-sure-is-jev) — collapse a raw probability distribution into one "sureness" score using margin, entropy and Gini together, rather than a single threshold on the top value.
- [bgrablin/hermes-switchyard](https://github.com/bgrablin/hermes-switchyard) — group-then-reselect for catalogs above Jev's 255-option limit on a single choice question.
- [askjev (pZacca)](https://github.com/pZacca/askjev) — ask Jev which question *type* fits a request, instead of hand-picking choice/score/noul per case.
- [ctaxnagomi/dgui-hypermem](https://github.com/ctaxnagomi/dgui-hypermem) — log every Jev decision to an external dataset as a byproduct, building a training corpus over time without extra instrumentation work.
- [meetr1912/jev-arena](https://github.com/meetr1912/jev-arena) — an offline miscalibrated-stub oracle plus a live Brier/ECE/risk-coverage pipeline, kept as one project rather than two.
- [dtduc-git/jevassert](https://github.com/dtduc-git/jevassert) — treat disagreement between repeated labelling passes as a signal to clean the label, not the model.
- [furedea/reflex-state](https://github.com/furedea/reflex-state) — a small, cheap-model-backed "what changed, what's blocked" execution-state layer kept separate from and independent of the main model's context.

## What the ecosystem is mostly not doing yet

- Independently verified calibration is rare. Outside the three studies already in [`FINDINGS.md`](FINDINGS.md#4-calibration--does-09-mean-90), almost every "we measured calibration" claim in this corpus is the project's own team scoring its own labels.
- End-to-end cost measurement under realistic load is rare. Most repos measure the Jev call itself (fast, cheap) rather than the whole pipeline it sits inside; the one external measurement that checked total pipeline cost found it could rise, not fall — [pattern 6](#6-context-reduction-compaction-and-tool-output-sieves), sourced from [`FINDINGS.md`](FINDINGS.md#3-speed-cost-and-accuracy-claims).
- Synthetic-only evaluation is still the default. Only a handful of projects — [Nyarlathoteppppp/pi-jev-context](https://github.com/Nyarlathoteppppp/pi-jev-context), [JYeswak/jev_playground](https://github.com/JYeswak/jev_playground) — went back and re-measured on real sessions after a synthetic benchmark looked good, and both found the real number was substantially worse (see [pattern 6](#6-context-reduction-compaction-and-tool-output-sieves) and [pattern 9](#9-calibration-and-evaluation-discipline)).
- Genuinely independent head-to-head benchmarks of a local reproduction against the real Jev API, scored on data neither side authored, are rare; most "beats Jev" comparisons in [pattern 11](#11-local-reproductions-of-jev-from-open-models) run on the challenger's own test set.
- Frozen, versioned regression sets for a Jev-based gate (so a prompt or threshold change can be checked against a fixed history of past decisions) appear in only a few projects in this corpus — 3, by grepping `data/repos.jsonl` for entries describing a record/replay or baseline+tolerance regression harness for Jev: [akanthed/jev-watch](https://github.com/akanthed/jev-watch), [dtduc-git/jevassert](https://github.com/dtduc-git/jevassert), [jeiel85/jevscope](https://github.com/jeiel85/jevscope) — not as a general convention.
